Do not deploy this intermediate manifest or use its old lockfile as a target installation.

## Concrete dependency and composition blockers

The full application install was attempted with the candidate manifest. Its scoped registry still points at the unavailable original server, despite a default registry override; that attempt was stopped after the 502 response. An explicit public default **and scoped** registry override then fails at the direct dependency `@nocobase/app-plugin-workflow@^1.0.0-beta.32` with `ERR_PNPM_NO_MATCHING_VERSION`. The public registry also lacks `@nocobase/app-plugin-ai-employee@1.0.0-beta.30`. No further install loop is warranted.

The available public Workflow `2.0.0-beta.1` and AI Employee `3.0.0-beta.2` both require `@nocobase/app-client@^2.0.0-beta.2`. The approved template requires client `^3.0.0-beta.2`; these ranges do not overlap. Installing those packages, forcing peers, retaining a second client, silently disabling old registrations, or enabling incomplete replacements would not preserve the application contract.

Consequently no valid target application lockfile was produced. `pnpm-lock.yaml` remains the original, unchanged evidence and is inconsistent with the intermediate target manifest. Do not edit it by hand or deploy with frozen installation. Regenerate and deduplicate it only after the complete compatible graph is available. The independent validation graph has its own generated lockfile and does not replace this file.

Client 3 removes the old Settings/Dev tree APIs and Users/API Keys page-mount options. The [client integration unit](client-unit.md) now adapts those consumers to unified contributions, retains separate shells and old grants/URLs, and adds application-owned Users/Roles/API Keys/Explorer pages. The language/session setup and a closed device-approval composition are included. Existing NocoHR business pages and styling remain in place. Other removed plugin administration surfaces and the approved replacement capabilities still need completion.

The smallest supported route forward remains independent capability and presentation work, followed by deployed inventories and archive/credential gates, then removal of retired registrations, generation of the valid application lockfile and complete startup/browser acceptance. An actual compatible retained-plugin release plus its migration contract is an alternative to that cutover. Neither branch is currently deployable.

## Verification and limits

Available public target dependencies were actually installed in an independent tooling directory, with exact CLI `.24`, server `.8`, client `.2` in major 3, Skills `.38`, testing `.4` and dev-config `.23`. That validation graph excludes retired AI/Workflow and discontinued Hub only in the tooling manifest; all three remain in the application manifest. A temporary ignored `node_modules` link exposes these tools to repository commands. This is a partial validation environment, not a successful application install.

- Six checks in two new repository test files pass against target packages, including the bounded guidance index and its links. They resolve the actual application configuration factories, check disabled replacement flags and server-only values, boot/shut down native Secrets/Mailer with a synthetic key, and reject a wrong record binding. The native migration verifier applies the byte-identical new device source, rolls it back and reapplies it while checking uniqueness, metadata/schema agreement and preservation of preceding synthetic rows.
- This exercises the real **new migration loader**. Its preceding synthetic sentinel is not a retained installation or an archive of old compiled tasks. Full application migration discovery/apply and checksum-preview commands stop at the unavailable Workflow import before database work.
- The changed server/configuration/test type subset passes. The preceding runtime/history selection ran 140 tests successfully and exposed four suites failing at the external jsdom setup module path. The client unit fixes that path through a local preset bridge; those affected suites now run in the target environment. No assertions, environments or timeouts are weakened. The independent prior validation package was rerun against the current source: all 217 existing checks pass (42 adapter/compiler, 94 history/HTTP, seven page actions, 74 process/artifact/preflight), with its own pinned dependencies and separate type checks. That separate runtime result remains distinct from target root component and full-application checks.
- The client project now type checks all adapted production contracts except the two missing retained AI/Workflow modules. Scoped client/configuration and component-test types are separately verified without shims. The earlier full repository diagnostics below are historical, not a fresh clean result. The initial full lint reports 142 errors and 20 warnings, including unadapted client contracts and previously unchecked application runtime code. Changed scaffold/configuration tests pass targeted lint; extending lint to the three adapted assistant files still reports two existing unsafe string conversions and an existing redundant stream assertion. Full formatting reports outstanding files; changed files are formatted separately without rewriting historical tasks.
- The actual target CLI build and strict source start fail while loading the retained AI CLI plugin. Strict compiled start reports the missing build output. Therefore complete login/HR permission composition, source/compiled application startup, full browser acceptance and English running-application screenshots are unverified. The client unit changes the named page sources; no deployment is changed.

The added application wiring introduces no poller, recurring job, heartbeat, takeover, node replay or business hot-path SQL. New secrets/configuration operations are in memory unless a later capability explicitly uses them. Per-request costs of the upgraded plugin versions remain unmeasured until the full composition can run. The device capability remains closed pending its independent authentication and session acceptance. Session cookie scoping can require signing in again at cutover. The database/keyring prerequisites must be checked on a backed-up installation before any real startup.

Before cutover, source changes can be reverted as a unit while the old runtime and history remain authoritative. This is not a data rollback procedure: if new migrations, encrypted credentials or business effects have been applied, retain them and use the verified compatible backup/runtime recovery plan. Never delete history or reassign migration ownership to make startup pass.
