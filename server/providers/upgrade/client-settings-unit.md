# Client settings continuity: `.74 → .76`

This unit brings the fixed `.76` list navigation, role list and shared status presentation into the existing NocoHR Settings pages. It adapts them to the application's current URLs and permission grants; it does not replace the Settings route tree or add another settings entry. The `.76` source archive SHA-1 is `a65772d58490af3392b2ce80d120731d115a5f11`.

## Retained application behavior

- `client/pages/settings/routes.ts` keeps the separate Settings navigation surface, page and action grant IDs, and current URLs. The target `.76` `user-detail.tsx` and `user-form.tsx` are not copied: the target collapses the current read-only detail route and its scope-specific `assign-role` cards into an edit flow. That changes both the existing navigation and permission presentation.
- Default access remains the application's split page at `client/pages/settings/default-access/{index,model,panel,api}.tsx`; it is not recreated because `.76` has a composite file layout. Its route and component tests remain in place.
- Sign-in return remains `client/routing/sign-in-return.ts`; it already handles the application redirect contract, base path and unsafe destinations. The target's differently named helper is not added as a second return path.
- The target's `setup-readiness` and `required-role-setup` components are not added as unused setup UI. They have no runtime consumer in the target application composition.

## Verification and costs

- Client TypeScript, changed-file ESLint and Prettier checks pass. The targeted settings run passed 32 tests across the list, URL-state, existing settings, route-grant and default-access suites. The sign-in-return unit selection passed 13 tests. The full sign-in-return component file has six existing integration failures: its test harness cannot resolve the `useRealtimeTopic` service, so the route renders empty; sign-in-return code is unchanged.
- Component tests cover direct Settings URLs with query state, user/role page transitions and browser Back. They cover no-access and HTTP 403 states without exposing an empty table, loading and read-only empty states, and HTTP 400 feedback. A fresh local development server reached `http://127.0.0.1:13000/main/` with an isolated temporary SQLite file, but startup began mail relay/sync work against rows in that new local database; the run was stopped when observed. Its exact request/write cost and whether a provider connected were not measured. No authenticated browser session was available, so direct browser refresh, actual authorized/denied page rendering and English screenshots remain unverified; no password or session file was read.
- The users list adds one `GET users/options` request per list mount. The role filter changes parameters on the existing `GET users` request; URL pagination/sorting and the role table add no endpoint. The added code creates no persistent state, migration, database write, lock, transaction or poll. SQL reads caused by `users/options` were not instrumented.
- The role table, status badges, links and filters change the visible Settings pages. Capture one English screenshot per changed page after signing into the local preview. The local development run is isolated from production and used no production credentials or services.
- `defaultTemplateVersion` remains `.54`; the application lock, 138 historical migration/seed files, application data, feature gates and preflight are unchanged. Full installed-data, Knowledge, Workflow, old-history and backup/recovery acceptance remains outside this unit; PR #2 stays draft and cannot merge or deploy.
