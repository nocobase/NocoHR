## Two precise proposals awaiting scope confirmation

**Recommendation: local date refresh.** In `client/pages/talent/sessions/index.tsx`, initialize a local date state lazily. Schedule one timeout for the next local midnight using the next calendar date (not a fixed 24-hour duration), recalibrating on window focus and document visibility restoration. Clean up timer/listeners on unmount. Today highlighting currently changes only when some other render happens; the proposed user-visible difference is that an open calendar updates across midnight without interaction, including after background suspension. Month navigation remains independent. Accept with controlled local-midnight, background-return, month-navigation, DST and unmount checks. Cost: one browser timer plus listeners, zero HTTP/SQL/model/write/transaction/claim cost. This behavior improvement is proposed only, not implemented or represented as equivalent lazy initialization.

**Recommendation: additive report row identity.** In `server/providers/hr/insight-service.ts` and `client/pages/talent/training-reports/index.tsx`, add a read-only `rowKey: string` to each existing authorized detail projection and use it as the React key. Completion/overdue/path rows use the assignment ID; exam rows use employee+exam; missing qualification rows use employee+qualification; expiring/expired certificates use the employee-certificate holding ID; gaps use gap ID; attendance uses enrollment ID; practice uses practice ID. Prefix keys by the detail category. These are source identities already available in the existing query results, not names, array positions or content hashes. Normal users may have same-name employees/courses or multiple certificates; distinct rows must retain identity after filtering/sorting. Keep displayed columns and exports unchanged. Accept with duplicate names/certificates, filter/sort stability, every detail category, and unchanged department/record authorization. Cost: one response string per detail row; zero additional SQL, model calls, persistent writes, transactions or storage fields. This small additive API contract is proposed only; no server response/type changes are implemented here.

No new storage, migration, authorization policy, scheduler/claim/lease/retry mechanism, dependency or lock change is needed by either proposal. Neither random keys nor rule suppressions are recommended.
